# Docker 端口、容器网络与安全访问

标签：#技术知识 #Docker #部署 #容器化 #网络 #运维

## 核心结论

Docker 容器里的端口可以重复；同一台服务器对外使用的端口不能重复。

理解这件事的关键，是把下面三层分开看：

```text
服务器（宿主机）
  -> Docker 网络
    -> 容器
      -> 应用监听的端口
```

例如两个 MySQL 容器都可以在各自容器内监听 `3306`，但它们不能同时把这个端口映射成服务器的 `3306`。

## 用一栋楼理解 Docker

可以把部署环境想成一栋楼：

| 概念 | 比喻 | 例子 |
| --- | --- | --- |
| 宿主机 | 整栋楼 | 一台 ECS 服务器 |
| Docker 容器 | 楼里彼此隔离的房间 | `llm-router-mysql`、`deeptrip-mysql` |
| 容器端口 | 房间里的门 | MySQL 的 `3306`、Router API 的 `8000` |
| 宿主机端口 | 楼对外的门牌号 | `服务器:80`、`服务器:3306` |
| Docker 网络 | 房间之间的内部走廊 | `router-data`、`platform-internal` |

不同房间都可以有一扇叫 `3306` 的门，因为它们在不同容器里；但是整栋楼对外不能同时有两扇都叫 `3306` 的门。

## 容器端口和宿主机端口

### 容器内部端口可以重复

下面两个容器可以同时运行：

```text
llm-router-mysql 容器：3306
deeptrip-mysql 容器：  3306
```

它们互不冲突，因为每个容器都有自己的网络空间。

同一个 Docker 网络中的应用，通常通过服务名加容器端口访问，例如：

```text
Router API -> mysql:3306
```

这里的 `mysql` 是 Docker Compose 中的服务名，不是服务器公网地址。

### 宿主机端口不能重复

Docker Compose 中：

```yaml
ports:
  - "3306:3306"
```

表示：

```text
服务器:3306 -> 某个容器:3306
```

此后外部客户端可以访问 `服务器地址:3306`。同一台服务器只能有一个服务占用宿主机 `3306`；第二个容器也尝试使用 `3306:3306` 时，会因端口被占用而启动失败。

如果第二个项目确实需要让外部访问它的 MySQL，可以映射为不同的宿主机端口：

```yaml
ports:
  - "3307:3306"
```

此时访问关系是：

```text
服务器:3307 -> 第二个 MySQL 容器:3306
```

容器内部仍然是 `3306`，改变的只是服务器对外使用的门牌号。

## 不写 `ports` 表示什么

如果 Compose 中没有 `ports`：

```yaml
services:
  mysql:
    image: mysql:8.4
```

MySQL 仍在容器内监听 `3306`，同网络中的容器仍能访问它；只是服务器外部不能用 `服务器地址:3306` 直接访问。

这通常更安全，尤其适用于数据库、Redis 等不需要让外部客户端直接连接的服务。

不要把“没有映射宿主机端口”理解成“没有端口”。正确理解是：端口只存在于容器和 Docker 内部网络中，没有对服务器外部开放。

## 以 DeepTrip 和 LLM Router 为例

当前服务器上的结构可以理解为：

```text
DeepTrip MySQL
  服务器:3306 -> deeptrip-mysql:3306

LLM Router MySQL
  仅 Router 内部网络 -> llm-router-mysql:3306

LLM Router Redis
  仅 Router 内部网络 -> llm-router-redis:6379

LLM Router API
  Docker 内部 -> llm-router-api:8000
  通过 platform-internal 供接入产品访问
```

因此，DeepTrip 的 MySQL 和 LLM Router 的 MySQL 都使用容器内 `3306`，但没有冲突：前者占用了服务器的 `3306`，后者没有映射到服务器端口。

## 三种访问内部服务的方式

### 1. Docker 内部网络访问

适合：同一台服务器上的服务互相调用。

```text
DeepTrip API
  -> platform-internal
  -> http://llm-router-api:8000/v1
```

优点：不经过公网，不需要把 Router API 端口开放到服务器外。

### 2. SSH 隧道访问

适合：管理员偶尔从自己的电脑访问生产管理页面。

```text
浏览器
  -> 127.0.0.1:18010
  -> SSH 加密通道
  -> 服务器内的 llm-router-api:8000
```

浏览器访问的是自己电脑的 `127.0.0.1:18010`，不是服务器公网端口。SSH 终端关闭后，通道立即消失。

优点：不用新增服务器入口，适合单人、低频管理；缺点：每次访问前都要建立隧道。

### 3. Nginx 反向代理访问

适合：需要固定地址、频繁使用或多人管理。

```text
管理员电脑（Tailscale）
  -> 服务器:80 或 443
  -> Nginx
  -> Router API
```

Nginx 类似门卫：它接收浏览器请求，再转发给内部的 Router。它可以只允许 Tailscale 网络访问，并保持 Router API 本身不直接暴露。

优点：可以使用固定域名或固定地址；缺点：需要维护 Nginx 配置、访问白名单和容器重建后的转发目标。

## Tailscale、SSH 和 Nginx 分别做什么

| 工具 | 解决的问题 | 适合场景 |
| --- | --- | --- |
| Tailscale | 把自己的电脑和服务器放进一个私有加密网络 | 远程运维、内部访问 |
| SSH | 安全登录服务器，也能临时建立端口隧道 | 单人、低频管理 |
| Nginx | 给内部服务提供固定入口并做访问控制和转发 | 多人、频繁访问、固定域名 |

它们可以一起使用：Tailscale 限定谁能到服务器，Nginx 决定如何转发请求，Router 管理页面仍用 Admin Key 做应用层鉴权。

## 生产环境的简单原则

- 数据库和 Redis 默认不要映射宿主机端口。
- 同服务器项目通过独立 Docker 网络和服务名通信，不依赖容器 IP。
- 容器 IP 会变化，不要把它当成长期配置。
- 偶尔管理生产服务：优先 SSH 隧道。
- 需要固定管理地址：再增加只允许 Tailscale 访问的 Nginx 反向代理。
- 即使只在内网访问，管理页面也要保留 Admin Key，不要把它当作唯一防线。
